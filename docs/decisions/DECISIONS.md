# Décisions : quiz-live-angular

Une entrée = un titre `## #N`. Les plus récentes en bas.

## #1 — Source de vérité du CDC : `docs/specs/`
`quiz-buzzer-docs` est archivé : les spécifications vivent désormais dans ce dépôt (`docs/specs/`). Toute modification de CA se fait dans la PR de la session qui l'exige. (2026-11-01)

## #2 — Une seule erreur « connexion perdue » hors 401 au démarrage (CA-25)
`POST /api/v1/token` : 401 → identifiants invalides ; toute autre cause (délai, serveur injoignable, autre non-2xx) → connexion perdue. Choix d'Olivier (« plus parlant »). Contrepartie : le proxy de dev renvoie 500 quand le hub est éteint, un vrai 500 du hub et un hub éteint sont indiscernables. La variante « erreur serveur » n'est plus utilisée au démarrage. (#14)

## #3 — Pas de `provideHttpClient` tant que le CA-4 n'est pas traité
L'hypothèse du récap (injection de `HttpClient` en échec au lancement) est fausse : `HttpClient` est `providedIn: 'root'` en Angular 21.2. `provideHttpClient(withInterceptors([authInterceptor]))` n'a d'effet observable qu'avec une requête authentifiée ; il viendra avec le CA-4. (#14)

## #4 — Délai maximal de 10 s sur le POST initial (CA-24)
Valeur choisie par Olivier parmi 5, 10, 15 et 30 s. Pas de mesure de référence : mesuré à 10,07 s en navigateur (Edge, proxy de dev). Pas de retry automatique (CDC). (#14)

## #5 — `initialize()` en `Promise<void>`, échec absorbé
Le CDC (l.98, l.185) impose une `Promise` pour que l'initialiseur soit strictement bloquant. L'échec est absorbé (erreur posée dans `ErrorService`) : un rejet empêcherait le démarrage de l'application. La navigation vers `/error` reste au CA-3. (#14)

## #6 — Numérotation des critères ajoutés
CA-24 et CA-25 de US-ANG-001 sont numérotés en fin de série (aucune renumérotation, aucune référence cassée) mais placés après le CA-3 qu'ils précisent. (#14)

Olivier veut propager : on propage les **règles de relevé**, les colonnes restent propres à chaque dépôt (une matrice Angular n'a pas de sens pour un hub ou un firmware). Une session par dépôt. ## #9 — Le token n'est lu que par `getToken()`, le signal reste privé
CA-2 : `AuthService` expose `getToken()` et `isReady()` ; le signal n'est plus exposé. `authInterceptor` lit `getToken()`. `isReady()` est dérivé de la présence du token (pas d'état séparé, YAGNI). Choix d'Olivier de rendre le signal privé tout de suite, malgré le port `TokenProvider` du WebSocket qui n'est plus satisfait par `AuthService` (voir `DEBTS.md`). (chore(authentication): expose the session token and its readiness)

## #10 — `authInterceptor` branché globalement, sans filtre d'origine
CA-4 : `provideHttpClient(withInterceptors([authInterceptor]))` dans `appConfig` ; l'en-tête `Authorization` est posé sur toutes les requêtes `HttpClient` dès qu'un token existe, comme le CDC l'écrit. Lève la réserve de la décision #3. Le POST du token passe sans en-tête (`getToken()` vaut `null` à ce moment-là). Contrepartie, choix d'Olivier de suivre le CA tel quel : le JWT partirait aussi vers une origine tierce ; aucune n'existe aujourd'hui, la dette est tracée dans `DEBTS.md`. Commit `chore` : aucun effet observable en prod avant la première requête authentifiée. (chore(authentication): attach the session token to every request)

## #11 — La navigation vers `/error` est un effet de l'application, enregistré dans `appConfig`
CA-3 : un `effect` (via `provideEnvironmentInitializer`) navigue vers `/error` dès que `ErrorService.currentError()` est non nul. Ni dans `AuthService` ni dans `ErrorService` (état et routage restent séparés), ni dans `App` (le test de câblage n'instancie pas `App`). L'effet vaut pour toute erreur future (CA-5, `game-corrupted`…), pas seulement l'échec du token. La route `/error` est vide (`children: []`) pour le moment : `<app-error-page />` reste dans `app.html`, un rendu par la route le doublerait. Elle n'a pas de guard (CA-23). Retrait de `app.html` : session suivante. (feat(error): navigate to the error page when the session cannot be opened)

## #12 — La racine mène au tableau de bord par une redirection déclarative, pas par une navigation après l'init
CA-21 (« après initialisation réussie, le Router navigue vers `/dashboard` ») et CA-22 (« une URL protégée au démarrage est accessible directement ») : une navigation impérative inconditionnelle après l'initialisation écraserait l'URL d'un rechargement (CA-22). Route `{ path: '', pathMatch: 'full', redirectTo: 'dashboard' }` : elle ne touche que `/`, et la navigation initiale du Router attend l'initialiseur bloquant (CA-1) — vérifié au navigateur (faux hub) : le guard laisse passer à la première navigation. Aucun code d'orchestration. Contrepartie : « Retour à l'accueil » mène à `/` donc à `/dashboard`, et si la session n'est pas prête (seul cas où la page d'erreur apparaît aujourd'hui) le guard renvoie vers `/error`, page vide : le bouton reste un cul-de-sac (voir `DEBTS.md`). (feat(routing): open the dashboard when the application starts at the root)


## #13 — « Retour à l'accueil » ne perd pas la cause de l'erreur tant que la session n'est pas prête
Option B retenue par Olivier. `ErrorPage.goHome()` n'efface l'erreur que si `AuthService.isReady()` est vrai ; sinon la variante d'origine (`invalid-credentials` ou `connection-lost`) reste affichée quand le guard renvoie vers `/error`. Option A écartée : un `authGuard` qui signale `connectionLost()` aurait rendu la page lisible mais faux (un 401 au démarrage serait affiché « connexion perdue »). Contreparties : `ErrorPage` dépend d'`AuthService` (voir `DEBTS.md`), et le bouton reboucle sur `/error` tant que la session n'est pas prête. Lève le choix laissé ouvert par la décision #12. (fix(error): explain why the dashboard is unavailable when the session is not ready)


## #14 — Le message « connexion perdue » ne promet pas de reconnexion et ne donne pas de consigne
Choix d'Olivier : retirer la dernière phrase (« Nous tentons une reconnexion automatique. »), le CDC interdisant tout retry de l'initialisation (CA-24). Variante écartée : la remplacer par une consigne (« Rechargez la page ») : une promesse de plus tant que le bouton de la page ne relance rien (voir `DEBTS.md`). Le texte reste valable pour le démarrage ; le WebSocket (US-ANG-010) aura besoin d'un message propre. Aucun CA ne cite le texte : le CDC n'est pas modifié. (fix(error): remove the automatic reconnection promise at startup)


## #15 — La variante `invalid-credentials` est rouge (`--semantic-danger`), le CDC étant muet
Le CDC (CA-25), la maquette de la page d'erreur (4 variantes) et la section 14 du design system ne disent rien de la couleur de cette variante, ajoutée avec CA-25. Choix d'Olivier : `--semantic-danger` (rouge), au sens que le design system donne à ce jeton (« invalidation, suppression ») ; un refus d'authentification rend l'application inutilisable, ce qui exclut l'ambre (« alertes douces »). Bloc calqué sur `server-error`. Variante écartée : `--semantic-warning` (ambre, comme `connection-lost`). Contrepartie : `server-error` partage la même couleur, seuls l'icône (`shield-x`), l'eyebrow et le titre les distinguent. Le design system et la maquette ne sont pas modifiés (voir `DEBTS.md`). (fix(error): make the invalid credentials title readable)


## #16 — Le port `TokenProvider` lit le token par `getToken()`, pas par un signal
Réconcilie la dette ouverte par la décision #9 : on adapte le consommateur (`WebSocketService`) plutôt que de rouvrir le signal d'`AuthService`. Port : `getToken(): string | null` (CA-10 : « lu depuis `AuthService.getToken()` au moment de la reconnexion »). Choix d'Olivier : renommage minimal. Variante écartée : scinder le port en lecture et refresh, pour qu'`AuthService` en satisfasse déjà une moitié ; un paramètre de constructeur de plus avant que le besoin existe. Contrepartie : `AuthService` ne satisfait toujours pas le port (`refresh()` manquant, CA-11/12) et aucun test ne le prouve (voir `DEBTS.md`). Commit `chore` : `WebSocketService` n'est injecté nulle part, aucun effet observable. (chore(websocket): align the token port with the authentication service)


## #17 — `refresh()` obtient un nouveau token sans rien signaler : l'échec revient à l'appelant, le token courant est conservé
Le port `TokenProvider` (`refresh(): Promise<void>`) est satisfait par `AuthService.refresh()`, qui rejoue le `POST /api/v1/token` d'`initialize()` (même corps, même délai de 10 s, via une méthode privée commune). Succès : le nouveau token remplace l'ancien. Échec (401, 5xx, réseau, délai) : la promesse est rejetée avec l'erreur d'origine ; le token courant et `isReady()` ne changent pas ; `ErrorService` n'est pas appelé, contrairement à `initialize()`. Choix d'Olivier : conserver le token et `isReady()`. Raison : la gestion de l'échec (3 tentatives à 5 s, puis fermeture et reconnexion complète) appartient à CA-15, et `refresh()` ne doit pas décider seul d'afficher `/error` pendant une partie. Variante écartée : effacer le token à l'échec, qui aurait fait basculer `isReady()` à faux et le guard vers `/error` au premier raté. Contreparties : un token déjà refusé reste « prêt » (voir `DEBTS.md`) ; deux `refresh()` simultanés émettent deux requêtes. Commit `chore` : `refresh()` n'a aucun appelant en production (`WebSocketService` n'est injecté nulle part). (chore(authentication): refresh the session token on demand)


## #18 — Le message `auth` part à l'ouverture de la socket, et le token est lu à ce moment
CA-7 : un vrai `WebSocket` lève `InvalidStateError` si `send()` est appelé avant l'ouverture. `SocketLike` gagne `onopen`, et `connect()` n'envoie plus rien tant qu'il n'est pas déclenché. Le token est lu dans `onopen`, pas à la construction : après un `refresh()` ou un backoff, c'est la valeur la plus fraîche (CA-10 : « au moment de la reconnexion »). Choix d'Olivier : cadrage validé à la porte 1. Variante écartée : lire le token à la construction et l'envoyer plus tard, qui garde une valeur potentiellement périmée au moment de l'envoi. Contreparties : `onopen` ne prouve pas l'authentification (seul `auth_success`, CA-8, le fait), et le service n'a toujours pas tourné sur une vraie socket (voir `DEBTS.md`). Commit `fix` : correction d'un défaut réel, sans changement de comportement observable depuis l'application, faute d'appelant. (fix(websocket): send the auth message once the socket is open)


## #19 — La socket s'ouvre à la fin du démarrage, sans le bloquer, et seulement si la session est prête
`provideAppInitializer` enchaîne `AuthService.initialize()` puis, si `isReady()`, `WebSocketService.connect()` ; il n'attend pas l'ouverture de la socket ni `auth_success`. Le service est fourni par une fabrique (`new WebSocketService(WEB_SOCKET_CONSTRUCTOR, environment.wsUrl, AuthService, navigateur d'erreur)`) ; `WEB_SOCKET_CONSTRUCTOR` (`providedIn: 'root'`, `WebSocket` natif) permet de substituer la socket dans les tests. `SocketLike.onopen` reçoit un `Event` : sans cela, le `WebSocket` natif n'était pas assignable au contrat (constaté au compilateur). Choix d'Olivier : cible A seule, initialiseur non bloquant, `wsUrl` de développement `ws://localhost:3000/ws` (le proxy de `ng serve` ne couvre que `/api`, la socket joint donc le hub directement). Écart signalé à la porte 1 : la valeur de production est `wss://set-by-ci.invalid/ws` et non `set-by-ci`, qui n'est pas une URL (`new WebSocket` lèverait `SyntaxError` au démarrage) ; le domaine `.invalid` est réservé et ne résout jamais, la connexion échoue donc proprement jusqu'à l'injection par la CI/CD. Variantes écartées : un initialiseur qui attend `auth_success` (un hub muet retarderait l'écran, alors que CA-24 borne déjà le démarrage à 10 s) ; un proxy `/ws` avec `ws: true` (plus de configuration, et `new WebSocket` exige de toute façon une URL absolue). Contreparties : l'`ErrorNavigator` est factice (code `4004` muet), une exception synchrone du constructeur de socket empêcherait le démarrage, et les codes de fermeture `4002` et `4004` n'ont pas été observés sur un vrai hub (voir `DEBTS.md`) ; le chemin nominal, la coupure et la reprise l'ont été au smoke test du 2026-11-07. (feat(websocket): connect to the hub once the session is ready)


## #20 — Le délai de reconnexion repart de 1 s à la réception de `auth_success`, pas à l'ouverture de la socket
CA-9 : « 1 s, 2 s, 4 s… ». Un `onopen` prouve que le transport est joint, pas que le hub a accepté la session ; seul `auth_success` (CA-8) signale une connexion aboutie. Le service remet donc son compteur de tentatives à zéro à ce message, et à aucun autre, y compris un message non JSON, qui reste émis sur `messages$` sans effet sur le délai. Contrepartie : le service lit le JSON de chaque message (voir `DEBTS.md`).

## #21 — Un `refresh()` rejeté sur un code `4002` n'empêche pas la reconnexion
CA-11 : le refresh précède la reconnexion, mais la spec ne dit pas quoi faire s'il échoue (CA-15 ne vise que le refresh proactif). Le service attend le refresh, avale son rejet et reconnecte quand même, avec le token courant et le backoff habituel. Variantes écartées : laisser le rejet remonter (la promesse du gestionnaire est rejetée sans capture et aucune reconnexion n'est armée, état actuel avant ce commit) ; fermer la connexion définitivement (rien dans la spec ne le demande pour CA-11). Contreparties : un token expiré repart vers le hub, qui refuse encore ; l'échec est silencieux (voir `DEBTS.md`). (fix(websocket): keep the connection attempts going when the token refresh fails)

## #22 — Un `token_expiring_soon` déclenche un `refresh()` en arrière-plan, sans relance, sans dédoublonnage, et son échec reste silencieux
CA-12 : à la réception de `token_expiring_soon`, le service appelle `refresh()` du port et n'en attend rien. Un rejet est capturé et ignoré : « silencieusement » exclut tout rejet non capturé, et les relances (3 tentatives à 5 s) relèvent de CA-15. Le message reste émis sur `messages$` comme les autres. Choix d'Olivier : CA-12 seul, CA-13 (renvoi du nouveau token par `auth_refresh`) dans la session suivante. Variantes écartées : partager le `refresh()` en vol entre un `4002` et un `token_expiring_soon` proches (de la logique dans `AuthService` ou le service sans besoin observé, chaque `POST` valide) ; attendre le refresh avant de continuer (rien ne bloque sur ce message). La lecture du type de message est mutualisée (`messageType`). Contreparties : le nouveau token reste local tant que CA-13 n'est pas fait, un échec ne laisse aucune trace (voir `DEBTS.md`). (feat(websocket): refresh the token when the hub announces its expiry)

## #23 — Un refresh réussi renvoie le nouveau token au hub par `auth_refresh`, sur la socket qui a reçu l'annonce
CA-13 : une fois le `refresh()` du port résolu, le service lit `getToken()` et envoie `{ "type": "auth_refresh", "token": ... }` sur la socket qui a reçu `token_expiring_soon`, sans la fermer. Un refresh en échec n'envoie rien. Les messages `auth` et `auth_refresh` sont construits au même endroit (`tokenMessage`). Choix pris sous le rouge, à challenger en revue de PR. Variantes écartées : faire retourner le token par `refresh()` (changement du port `TokenProvider` sans besoin observé : `getToken()` suffit, voir `DEBTS.md`) ; envoyer sur la socket courante du service plutôt que sur celle de l'annonce (le service ne garde pas la socket ; une reconnexion entre-temps ferait partir un `auth_refresh` sur une session non authentifiée) ; vérifier que la socket est encore ouverte avant d'envoyer (aucun besoin observé, la fermeture déclenche la reconnexion). Contreparties : le token envoyé est relu après le refresh, un `send` en échec est avalé (voir `DEBTS.md`). (feat(websocket): send the refreshed token to the hub)


## #24 — Le refresh du token se smoke-teste contre un faux hub écrit dans le dépôt, tant que le hub n'implémente pas US-021
Le hub n'émet pas `token_expiring_soon` et ignore `auth_refresh` (constaté dans `ws-route.ts` du hub, `deb5465`) : le smoke test prévu à la fin de CA-13 est impossible sur un vrai hub. `scripts/fake-hub.mjs` (Node seul, aucune dépendance, WebSocket RFC 6455 minimal) sert `POST /api/v1/token` et `/ws`, envoie `token_expiring_soon` après un délai réglable, puis rend un verdict (PASS/FAIL, code de sortie) : `auth_refresh` reçu avec le dernier token émis, sur la connexion existante ; ou, avec `--fail-refresh`, un refresh tenté sans `auth_refresh` envoyé. Choix d'Olivier : option 1 parmi trois (faux hub ; CA-16 sans preuve possible ; implémenter US-021 dans le hub). Variantes écartées : ajouter `ws` en dépendance du dépôt (dépendance et audit de plus pour un outil de smoke test) ; un proxy devant le vrai hub (le vrai hub n'émet rien à relayer). Contreparties : le faux hub valide ma lecture de la spec, pas le hub ; la preuve réelle exige US-021 côté hub (voir `DEBTS.md`). (chore(scripts): add a fake hub to smoke-test the token refresh)

## #25 — Un refresh proactif en échec est relancé deux fois à 5 s, puis la socket est fermée (code 1000) et la reconnexion repart
CA-15 : si `refresh()` échoue après un `token_expiring_soon`, le service réessaie après 5 s, au plus 3 appels au total ; au 3e échec il ferme la socket avec le code 1000 (`close(1000, 'Token refresh failed')`, ajouté au port `SocketLike`), et le `onclose` existant arme la reconnexion avec le backoff habituel, qui reprend à l'authentification (CA-9). Un retry réussi envoie `auth_refresh` comme CA-13. Une socket déjà fermée (par le hub, qui ferme en `4002` juste après `token_expired`) ne relance plus rien, n'envoie plus rien et n'est plus fermée : le service tient un `WeakSet` des sockets fermées. Choix pris sous le rouge, à challenger en revue de PR. Variantes écartées : 3 relances, soit 4 appels (la spec dit « après 3 échecs ») ; un code applicatif 4xxx pour la fermeture (réservés au hub) ; un port de temps injecté (`setTimeout` et les faux timers de Vitest suffisent, comme pour le backoff) ; annuler les minuteries à la fermeture (la garde au tir suffit, voir `DEBTS.md`). Contreparties : l'échec reste silencieux, la reconnexion repart avec le token courant, deux annonces rapprochées lancent deux boucles (voir `DEBTS.md`). (feat(websocket): retry the token refresh three times before reconnecting)


## #26 — Le timer d'expiration du token appartient au hub : CA-14 n'appelle aucun code Angular
CA-14 (« le timer de refresh est réinitialisé ») supposait un timer côté client. Il n'en existe pas : le refresh proactif est déclenché par `token_expiring_soon`, émis par le hub (CA-12), et jamais par une minuterie d'Angular. Le hub arme et réinitialise son propre timer d'expiration ; à la réception de `auth_success` après `auth_refresh`, Angular n'a rien à réarmer, son prochain refresh attend la prochaine annonce. Le seul traitement d'`auth_success` côté Angular reste la remise à zéro du délai de reconnexion (décision #20, CA-9). Choix d'Olivier : confirmé en chat le 2026-11-08, le hub possède le timer. Confirmé aussi par la spec du hub `US-021-token-refresh.md` : à `auth_success`, le hub arme deux timers par connexion (CA-1, CA-5) ; un `auth_refresh` valide les annule et les réarme depuis le `exp` du nouveau token (CA-11) ; le client n'en gère aucun. La spec `US-ANG-001` (CA-14) est reformulée en conséquence. Variantes écartées : un timer de refresh côté Angular, redondant avec l'annonce du hub et source de deux refresh concurrents (voir `DEBTS.md`) ; laisser CA-14 en ❌ dans la matrice, qui ferait chercher un code qui ne doit pas exister. Contrepartie : `US-ANG-010` CA-34 parle encore de « nouveau `expires_in` » (voir `DEBTS.md`). Commit `docs` : aucun code ne change. (docs(decisions): record that the refresh timer lives on the hub)

## #27 — `token_expired` n'a aucun traitement propre : seule la fermeture `4002` déclenche le refresh
CA-16 : le hub envoie `token_expired` puis ferme en `4002` (spec hub US-021, décision #25) ; Angular ne lit pas `token_expired` et laisse la fermeture `4002` faire un seul `refresh()` puis une seule reconnexion (CA-11). Un traitement de `token_expired` qui appellerait `refresh()` le doublerait. Le test `should refresh the token once and reconnect once when the hub announces the expiry then closes with 4002` verrouille la séquence ; né vert, il a été prouvé par mutation (un handler naïf de `token_expired` qui appelle `refresh()` le fait échouer : 2 appels au lieu d'1 ; un handler qui appelle `connect()` aussi : 3 sockets au lieu de 2). La spec `US-ANG-001` (CA-16) est reformulée en conséquence. Le type de commit `test` (test seul, sans code de production) est ajouté à `CLAUDE.md` et à `docs/method/WORKFLOW.md` de ce dépôt. Choix d'Olivier : option `test` pour le type, reformulation de CA-16 dans cette session. Variantes écartées : `chore(websocket): …` (le type `chore` désigne du code dormant ou de l'outillage) ; un handler de `token_expired` qui ferme la socket lui-même (le hub la ferme déjà, et deux fermetures concurrentes rouvrent le risque de double reconnexion). Contreparties : si un hub n'envoyait `token_expired` sans fermer en `4002`, Angular ne ferait rien (voir `DEBTS.md`). (test(websocket): lock the token_expired then 4002 sequence)

## #28 — La fermeture `4004` affiche une page d'erreur dédiée `session-replaced`
Quand le hub ferme la socket en `4004` (un autre onglet, ou un autre client du même compte, a repris la session ; hub `US-009` CA-17), `WebSocketService` n'essaie plus de se reconnecter (inchangé) et signale désormais l'erreur via `ErrorService.sessionReplaced()` ; la navigation vers `/error` reste faite par l'`effect` unique de `app.config.ts` (CA-3), sans second appel au `Router`. Choix d'Olivier : cible `feat(error)` pour `4004`, variante dédiée `session-replaced` plutôt qu'une variante existante, message « Votre session a été ouverte dans un autre onglet. Fermez celui-ci ou rechargez la page pour reprendre la main. ». Choix de Claude, non validés : surtitre « Session remplacée », titre « Un autre onglet a pris la main », icône `app-window`, ton ambre (celui de `connection-lost`) car ce n'est pas une panne. Variantes écartées : réutiliser `connection-lost` avec un autre texte (cette variante doit rester vraie pour la reconnexion de `US-ANG-010`, voir la note de la décision #14) ; un `Router.navigate` direct dans le navigateur d'erreur (deux chemins de navigation vers `/error`). Observé sur le vrai hub par Olivier le 2026-11-08 (deux onglets, F5 inclus). Contreparties : « Retour à l'accueil » mène à un tableau de bord sans socket, et le hub ne journalise pas le remplacement (voir `DEBTS.md`). (feat(error): explain that the session was taken over by another tab)
